# DEVELOPMENT-EVENT-001 — Identity can survive changing shape

This is an incubator specimen, not a promoted Static law.

It exists because several independent project surfaces now preserve the same
problem from different directions:

- BABYBODY asks what a thing can become when reality leans on it without
  squeezing out its life.
- BODY-BRIDGE records lawful deformation and relations differentiating by load.
- PaulaOS explicitly distinguishes **LANDING PLACE != NATURAL HOME** and
  **CONTAINER != ORGANISM**.
- Composer 002 separates **SHOWN != CHOSEN** and records recommendation exposure.
- The Living Git Map separates observed DELTA from curated RELATIONS, and
  VISIBILITY-APERTURE-001 demonstrates that one axis can change without
  rewriting status, authority, evidence, maturity, or identity.

The candidate compression is:

[
\boxed{\text{DEVELOPMENT} =
\text{IDENTITY-CARRYING TRANSFORMATION}
+
\text{WITNESSED DIFFERENCE}}
]

Pressure may be present. Pressure may motivate a proposal. **Pressure is not
automatically a causal explanation.**

> Pressure may propose a new body. Only witnessed transformation establishes
> that one formed.

## The receipt

A development event records:

```text
subject
event type
before
witnessed conditions / loads
after
invariants carried
properties changed
residue
sources
explicit non-claims
causation status
```

The key field is **invariants_carried**. A system claiming continuity must say
what actually supports calling the subject the same thing after change.

The machine-readable shape is
[`development-event.schema.json`](development-event.schema.json), with an
executable validator at
[`scripts/development_event.py`](../../../../scripts/development_event.py).

## Four candidate event families

### MOLT

A container or address changes while an explicitly evidenced identity continues.

[
(O,C_A) \rightarrow (O,C_B)
]

MOLT does not mean copy, delete, rename, fork, or migration merely because files
moved. It requires ancestry receipts and an explicit continuity claim.

### GUIDANCE

The possibility surface presented to an observer changes before action.

[
A_{o,t}\rightarrow S_{o,t}\rightarrow R_{o,t}\rightarrow C\rightarrow U
]

where **available** means available to the stated observer/instrument at the
stated time—not all metaphysically possible options.

Keep these separate:

```text
AVAILABLE != SHOWN != RECOMMENDED != CHOSEN != USED
NOT SHOWN != UNAVAILABLE
NOT CHOSEN != REJECTED
RECOMMENDED != PREFERRED
```

### DIFFERENTIATION

A relation retains addressable continuity while its connective form changes
under explicitly witnessed loads.

[
r_0 \rightarrow r_1
]

Endpoint persistence alone does not prove developmental continuity. The event
must cite the relation identity, old and new forms, and load receipts.

### APERTURE

Who may witness a subject changes while unrelated axes remain independent.

[
(X,V_A)\rightarrow(X,V_B)
]

A visibility change does not imply promotion, validation, maturity, canon, or
ontological change.

## Negative controls

These do **not** establish a development event by themselves:

```text
branch motion      != growth
PR closure         != maturation
copy               != migration
similar name       != identity
similar topology   != shared ancestry
recommendation     != preference
nonselection       != rejection
pressure before X  != pressure caused X
new container      != new organism
old container      != false history
```

## BAT FEED

The operational roaming prompt is in [BAT-FEED.md](BAT-FEED.md).

Bats should return **one bounded candidate event at a time**. If the evidence
cannot support continuity or witnessed difference, return **HOLD** and name the
missing witness rather than completing the pattern by imagination.

## Current status

**CROSS-PROJECT / INCUBATOR.**

There are multiple project-backed specimens, but this shared grammar has not yet
earned promotion into a portable Pattern. The next useful test is not another
analogy. It is repeated successful receipts across materially different event
families with meaningful negative controls.
