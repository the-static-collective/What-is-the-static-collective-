# 0.6.0AL — Keep Toast / Scrape Toast & Persistent Lineage

> **Status:** accepted interaction direction; repository implementation remains authoritative.
>
> **Project issue:** [the-haunted-toaster #207](https://github.com/the-static-collective/the-haunted-toaster/issues/207)
>
> **Builds on:** [#180 — Toastmood doors](https://github.com/the-static-collective/the-haunted-toaster/issues/180)

## The simplification

The ordinary creative loop should become:

```
load song
  ↓
generate six
  ↓
select one toast
  ↓
KEEP TOAST | SCRAPE TOAST
```

The person does not need to choose a mutation verb to keep playing.

**KEEP TOAST** accepts the selected candidate for the render path.

**SCRAPE TOAST** asks the Toaster to produce another six from the selected candidate.

The simplification is only at the human membrane. The machine keeps the deeper grammar.

## Six verbs stay under the hood

SCRAPE does not introduce a second mutation system. It consumes the existing deterministic six-move deck:

1. EXPAND
2. MUTATE
3. CONVERGE
4. STOMP
5. CROSS × deterministic partner A
6. CROSS × deterministic partner B

Each move contributes one deterministic, attributable outcome to the next visible six-up.

The verbs therefore disappear as mandatory questions and remain as executable provenance.

> **Complexity stays in the machine; choice stays binary for the human.**

A refusal is still evidence. If one hidden move cannot lawfully produce its contribution, the Toaster should preserve that refusal rather than silently replacing it with an unrelated candidate.

## Persistent lineage is part of 0.6.0AL

The current candidate loop can lose track of earlier generations. That should be treated as part of this interaction change, not deferred cleanup.

Every scrape should append a durable ancestry step:

```
previous generation
  → selected toast
  → hidden move / proposal
  → generated descendant family
  → surfaced child
  → next generation
```

At minimum the receipt chain should retain:

* prior receipt or generation address;
* parent family id/hash;
* selected candidate id/address;
* hidden move kind and proposal address;
* descendant family id/hash;
* surfaced representative id/address;
* deterministic policy/seed inputs required for replay.

After five scrapes, the fifth-generation toast should still have a lawful route back through generations four, three, two, one, and the original six.

The receipt is not merely a note about the latest parent. It is the branch history.

## Interaction law

* Selecting a thumbnail is selection only.
* The ordinary selected state exposes **KEEP TOAST** and **SCRAPE TOAST**.
* Verb controls are not mandatory UI in the ordinary path.
* SCRAPE executes the already-existing move deck beneath the surface.
* Every visible child remains attributable to exactly one hidden proposal.
* Back/return restores the exact prior family without severing lineage.
* Locks and source constraints remain absolute inputs to hidden moves.
* CROSS keeps deterministic partner selection.
* No AI or taste-ranking layer secretly chooses the six visible winners.

## Replay law

The same parent family, selected candidate, locks, deal index/policy, and accepted inputs should regenerate the same hidden proposal deck and the same surfaced descendants.

The Toaster should be able to answer both:

> **What made this toast?**

and

> **How did we get all the way here?**

The first is local provenance. The second is lineage.

## 0.6.0AL field phrase

> **Pick a toast. Keep it, or scrape it. The Toaster remembers every crumb.**

This page is a design projection. GitHub issue #207 and the eventual executable implementation remain the authority for what actually lands.
