# Haunted Toaster Beta — Toastmood Field & CROSS

Status: **project-backed beta frontier; queued behind the current renderer repair/stabilization line**

Canonical project issue: [Haunted Toaster #147](https://github.com/the-static-collective/the-haunted-toaster/issues/147)

## The shift

The current alpha interaction asks the human to choose a Toast Feel before generation. The beta hypothesis inverts that relationship:

> **Toastmoods should inform the six-up rather than require preselection before the six-up.**

The ordinary path becomes:

```
source witness
  + canonical Toastmood field
  + lawful constraints
        ↓
  diverse six-up
        ↓
  human recognition
        ↓
  optional A × B CROSS
        ↓
  six typed descendants
```

No default filter. No privileged baseline card. No requirement to understand the Toastmood vocabulary before seeing what the source can become.

The existing ontology remains intact:

> **Toast Feel biases the creature. It does not dictate the creature.**

What changes is where that bias is consumed.

## Toastmoods as a field, not furniture

The six-up should deliberately distribute candidates across meaningfully different Toastmood pressure regions while preserving the stronger base-diversity law already emerging in Haunted Toaster.

This is not a requirement to map six cards one-to-one onto six named moods. The goal is **meaningful family distance**:

* different base creature identities;
* different expressive pressures;
* different lawful interpretations of the same source;
* coverage before randomness;
* no hidden default candidate.

A good family should read as:

> **six substantially different hypotheses about what this source wants to become.**

## CROSS — two-parent candidate genealogy

After the human recognizes two charged candidates, those two may become explicit parents of a new six-up.

```
A ─┐
   ├─ CROSS → six descendants
B ─┘
```

CROSS is not whole-object averaging. It should use typed inheritance across the actual creative lattice, with an addressed crossover policy and inspectable per-child decisions.

A first family may distribute inheritance in forms such as:

* A structure + B atmosphere/expression;
* B motion + A material tendency;
* A dynamics + B topology where lawful;
* B temporal behavior + A texture/palette tendency;
* A-dominant / B-recessive;
* B-dominant / A-recessive.

Exact axis assignments remain project-owned implementation detail.

## Genealogy law

Ancestry belongs in the derivation/artifact envelope rather than being smuggled into canonical score semantics merely to prove breeding.

A CROSS derivation should preserve enough evidence to reproduce and inspect:

* parent A;
* parent B;
* crossover policy/version;
* inheritance plan;
* bounded mutation after inheritance, if any;
* descendant identities;
* accepted child lineage.

Same parents + same canonical inputs + same seed/policy must reproduce the same descendant family.

## Why two parents first

Two parents preserve causal legibility. When a descendant works, inheritance can still be inspected.

Three-or-more-parent composition remains deliberately fogged. If it later becomes useful, it should probably be a distinct operation rather than silently widening CROSS. Working metaphor: **COMPOST**.

## Sequencing boundary

This is **not** part of the current elastic-topology-response repair line.

PR #146 is under packaged field witness and the newest render behavior may need repair. Stabilize that renderer first. Candidate breeding is only meaningful when descendants can be rendered and compared through a trustworthy execution path.

So the near-term order is:

```
current packaged field test
→ render repair / stabilization as required
→ preserve trustworthy renderer behavior
→ beta candidate ecology: Toastmood-informed six-up
→ two-parent CROSS
```

## Stop condition

Graduate this from frontier when one ordinary session can:

1. reach a genuinely diverse six-up with **no Toast Feel preselection**;
2. reproduce that family from the same canonical inputs;
3. select exactly two candidates as parents;
4. CROSS them into six materially distinct, reproducible descendants;
5. inspect the resulting genealogy and inheritance without weakening locks, constraints, replay, or renderer authority.
