# Entrusted Corpus — Trust Archaeology as Architecture

Status: **incubating architecture / National Treasure archaeology**\
Date: **2026-08-19**

Project-owned repositories remain canonical for executable behavior. National Treasure holds the research case. This page preserves the cross-project architectural clue without promoting it into shared law.

## The clue

Trust archaeology keeps returning to a systems problem the Collective is already encountering from another direction:

> **How can something remain itself while the humans, accounts, machines, and containers temporarily holding it keep changing?**

The useful extraction is not “software should imitate trust law.” It is a sharper separation:

```
custody != corpus identity
control != authority
authority != benefit
authority != purpose
authorship != administration
copying evidence != copying authority
succession != retroactive identity
```

That leads to the current architectural hypothesis:

> **A durable project may need a purpose-bearing corpus surrounded by a succession-capable, accountable stewardship membrane.**

This is a hypothesis. It has not graduated into a Pattern.

## Why this door is relevant now

Corpus OS already contains a materially real executable specimen rather than only a metaphor. [Warranted Execution — Corpus OS Specimen](executable-membrane-javascript-encounter-surface/warranted-execution-corpus-os-specimen.md) records the landed composition:

```
proposal
  -> Trust admission
  -> ephemeral Action Warrant
  -> Session admission
  -> bounded host consequence
  -> receipt
```

That specimen already separates the authority question from the capability/execution question, makes the warrant one-shot, and explicitly keeps `legalValidity: unclaimed`.

Meanwhile [Lawful Reachability / Constituted Reality](lawful-reachability-constituted-reality.md) asks what present world is actually constituted rather than treating existing bytes as sufficient reality. The two lines now touch a much older institutional pressure: possession of the corpus, authority over it, benefit from it, purpose governing it, and continuity through successor stewards do not have to collapse into one identity.

The historical resemblance is useful. It is **not yet a genealogy claim**.

## Five veins to mine

### 1. Corpus

What is the durable subject?

For a software project, the answer may be larger than a current Git repository. GitHub can be a present projection/custody surface while the continuing corpus also includes adopted history, releases, receipts, keys, archives, recordings, documentation, and other constituted artifacts.

The design question is whether the system can say:

```
this repository is a current authoritative projection of corpus C
```

instead of silently assuming:

```
corpus C is whatever this account currently controls
```

### 2. Entrusted authority

Ordinary access control asks:

```
Can identity X perform operation Y?
```

Entrusted authority asks more:

```
Why may X exercise Y over this subject,
in what capacity,
under what originating authority,
for what declared purpose,
with what withheld powers,
what delegation law,
what exhaustion/expiry,
and what evidence must remain afterward?
```

This may be the older shape hiding underneath Conservation of Authority. Authority can be received, bounded, exercised, consumed where appropriate, refused, reviewed, removed, and succeeded. Merely copying its representation should not manufacture another live authority.

### 3. Purpose

A mechanically permitted action and a purpose-faithful action are not necessarily the same question.

That suggests two explicit surfaces rather than one opaque oracle:

```
FORM / ADMISSION
  declared law
  -> admitted / refused

PURPOSE / FIDELITY
  declared purpose + bounded evidence
  -> compatible / challenged / unresolved
```

The second surface must not fabricate legal invalidity or become an AI morality engine. A challenge can remain a challenge, trigger human review, require stronger authority, or become durable refusal evidence.

### 4. Accounting

Entrusted power without accounting eventually becomes indistinguishable from possession.

The relevant chain is already familiar:

```
received authority
  -> proposed exercise
  -> admission / refusal
  -> attempted consequence
  -> terminal outcome
  -> durable receipt
```

This is where trust archaeology may sharpen rather than replace the Collective's existing receipt/warrant machinery.

### 5. Succession

Succession is not merely password recovery.

A durable corpus should be able to ask what happens when:

* the founder dies or leaves;
* a maintainer becomes unavailable;
* a steward is removed;
* the hosting vendor disappears;
* keys are rotated or lost;
* an authoritative repository must migrate;
* stewardship changes while prior history must remain attributable to the actors who actually held it.

A successor should be able to become newly constituted without pretending to have been the previous actor all along.

## National Treasure owns the archaeology

The detailed case is being preserved in the `national-treasure` repository under `cases/trust-archaeology/`.

The research method uses two separate axes:

* provenance: **Observed / Primary source / Inference / Speculation / Failed**;
* support confidence: **Established / Probable / Possible / Unsupported**.

That separation matters here. A primary source can make a false claim. An elegant architectural inference can remain merely possible. A common historical story can remain unsupported until its transmission evidence is actually traced.

The initial case explicitly keeps Roman `fideicommissum`, English uses/Chancery, Islamic `waqf`, medieval/Germanic antecedent theories, and modern trust structure in separate source families until their relationships are earned.

## Downstream doors, not downstream law

The archaeology currently exposes bounded doors:

* **Corpus OS** — test whether the existing Trust Runtime is one specimen of entrusted authority rather than the universal model.
* **Project0** — test constituted corpus identity and authoritative projection without creating a second canonical identity law.
* **TranchNode** — test continuity through transformation, custody change, node loss, and re-projection.
* **Conservation of Authority** — sharpen standing power vs one-shot authority vs delegation vs exhaustion vs successor authority.
* **Refusal Topology** — preserve technically possible-but-unauthorized, purpose-challenged, exhausted, under-witnessed, and succession-gap worlds as constitutional negative space.
* **GitHub continuity** — model a repository as a current authoritative projection rather than the sovereign definition of the project.
* **Human legal consultation** — later ask which real-world assets, powers, licenses, fiduciary duties, tax consequences, jurisdictions, and succession mechanisms actually apply. Architecture does not answer those questions by itself.

## What must not happen

Do not:

1. rename RBAC roles `trustee` and `beneficiary` and call the problem solved;
2. let possession of bytes, credentials, or an admin account prove constituted authority;
3. let purpose become an ordinary editable description if it is supposed to constrain power;
4. let copied warrants or receipts duplicate authority;
5. treat succession as rewriting identity history;
6. let historical analogy become legal validity;
7. let GitBook outrank the project-owned executable source.

## Graduation gate

Do **not** build a shared Entrusted Authority framework yet.

The clue earns promotion only after:

1. Corpus OS demonstrates a materially useful entrusted-authority case;
2. a second, substantially different project reproduces the useful invariant without importing Corpus-specific semantics;
3. one real migration, re-projection, or succession specimen proves continuity under change;
4. failure/refusal behavior is demonstrated, not only the happy path;
5. copied representation cannot manufacture authority;
6. the shared residue is simpler than the local implementations it would replace.

Until then:

> **National Treasure keeps the archaeology. Project repos keep executable truth. GitBook keeps the constellation visible. Residual fog stays fog.**
